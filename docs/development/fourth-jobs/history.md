# 实施设计

状态：实施设计；其中已落地的接口约定见文末。任务状态统一维护在[实现进度](progress.md)，验收标准见[验收计划](acceptance.md)。

## 范围与职责

| 仓库／目录 | 计划职责 |
| --- | --- |
| Client | 职业目录与中文名、冒险工具、游戏属性界面、技能显示、渲染和资源映射 |
| Server | NPC 与职业规则、等级和点数、技能与状态、Game Control 校验和持久化 |
| Admin | 冒险工具接口授权与校验、请求转发、映射副本和自动化测试 |
| Gateway | 原则上复用现有资源服务及反向代理；仅在验证出具体缺口时修改 |
| 根仓库 | 跨仓库编排、资源审计、目录生成、方案与进度；集中 changelog 遵守仓库规则 |

职业 ID、上限和允许操作以服务端为最终权威；客户端不自行推算职业是否合法。展示目录应同时区分职业、性别和外观形态，不再让中文翻译表承担完整职业能力清单的职责。优先复用已有数据管线，确定需要新接口后才增加接口；避免为此扩展为通用配置平台。

## P0：支持范围与差异审计

交付物：20 个职业的规则与资源矩阵、技能差异清单、确定后的切换规则。

- 对照 Server 职业／技能数据库与 Client 定义，核对规范 ID、前置职业、性别、等级条件和特殊形态。
- 逐项检查 13 个常规四转和 7 个扩展职业；扩展职业不能统一套用普通四转的 200／70 条件。
- 核对数据库字段、运行服务版本与配置覆盖，确认当前等级、特性和 AP 数据链。
- 针对实际运行资源核查身体、武器、坐骑、机甲、技能图标及特效，记录缺失、来源、目标路径和哈希。审计产物放 `work/` 或 `artifacts/`。
- 明确当前服务端技能版本与现有资源的差异。保留 20211103 协议，不把升级 PACKETVER 当作默认解决方式。
- 形成中文职业名清单；新增名称使用项目认可的资料来源，未确认译名显式列为待定。

退出条件：目标职业及缺口清晰；不要求此时全部缺口已修复。

## P1：游戏内四转 NPC

交付物：可访问的中文统一转职入口，完整且可解释的准入检查。

- 复用 `npc/custom/jobmaster.txt` 已有规则，实施时确定直接完善原脚本，还是在 HappyRO 自有脚本中收敛为四转入口。默认避免额外开放无关转职、送装备等功能。
- 保留或选择明确主城坐标，检查与已有 NPC 冲突；配置实际加载，并同步 NPC 中文名、图鉴与导航生成结果。
- 核对常规职业的进阶三转要求、200／70、宝宝限制和性别规则。
- 为全部扩展职业明确前置和等级条件，补齐缺失路径，检查是否有无法达到的条件。
- 明确未用技能点、技能继承、转职后 Job 等级、装备与坐骑状态；复用服务端职业变更机制，不直接写数据库职业字段。
- 提供中文确认、条件不足说明与成功提示，避免重复点击导致重复发放奖励或点数。

退出条件：游戏内合法转职成功，非法转职被拒绝且说明准确；状态保存与重登一致。

## P2：冒险工具职业与等级闭环

交付物：可搜索、可切换的四转职业目录与可靠等级调整。

- 补齐中文职业名、普通／四转／扩展分组，过滤不可直接转职的骑乘和机甲形态。
- 由角色性别和服务端规则确定可选职业；服务端归一化后的职业必须回传并正确显示。
- 保留现有冒险工具授权边界，不因为开放四转而给普通角色增加管理权限；Admin 映射副本需注明来源并同步。
- 转职后重新读取快照，刷新 Base／Job 最大值、技能点和属性；错误时恢复可操作界面，避免展示未保存值。
- 修正 `character.progression.update` 的校验顺序：先解析目标职业，再确定目标等级上限，全部参数验证通过后执行变更。
- 对“转四转并升到 250”的同请求组合提供正确处理。对于从高等级四转切回低上限职业，建议默认拒绝超限组合并提示用户明确设置合法目标等级，不静默截断等级。
- 正式实现前核对职业切换函数的副作用与失败行为；不得先转职、后因参数错误返回失败却留下部分变更。
- 校验重复请求、快速连续操作和既有幂等机制，避免点数重复结算。

退出条件：目录、转职、等级、快照一致，支持 200→201 与目标职业最高等级；拒绝超限输入且角色状态无部分变化。

## P3：特性属性、点数、AP 与持久化

交付物：游戏内和冒险工具均可正确使用四转特性体系。

- 核对并复用 POW、STA、WIS、SPL、CON、CRT、特性点、AP／最大 AP 的服务端实现。
- Game Control 快照增加必要的特性值、可操作能力和上限；字段名及最终结构在实施时与现有接口风格统一。
- 为特性修改和重置建立明确操作，区分基础属性重置与特性重置。不能把普通洗点成功视为特性已重置。
- Admin 扩展对应请求校验、服务编排和测试；Client 增加特性面板和清晰的操作反馈。非四转角色不显示无效操作，服务端也必须拒绝。
- 明确普通游戏加点需要消费的点数，以及冒险工具直接设值的权限与点数规则；两种路径都不能产生负点数、溢出或重复奖励。
- 核对自然升级与工具调级时特性点的发放／回收，以及降级、换职业、重置后的合法状态。
- 验证 AP 自然获得、技能消耗和恢复；复用已有恢复操作，不无需求增加任意 AP 修改入口。
- 通过服务端内存状态与保存机制操作角色，验证退出、重登、地图切换后的结果；仅在证实数据库结构缺失时设计迁移。

退出条件：六项特性、特性点、AP、等级与职业一致，所有修改正确持久化。

## P4：技能、装备与显示补全

交付物：按职业记录的技能／资源修复与实战证据。

- 对照服务端技能树检查客户端技能 ID、中文名称、说明、图标、前置技能与等级。
- 按机制分类抽样验证施法方式、目标选择、消耗、冷却、伤害／治疗／状态／召唤效果及 AP 行为；共享路径不逐职业重复，独有机制及已发现缺陷单独验证。
- 检查 20211103 下相关封包、数值范围与界面刷新；无法在既定协议内正确实现的功能单列阻塞，不私自升级协议。
- 覆盖职业武器、盾、披风、染色、坐骑、狼、机甲和性别限制；形态改变不应破坏技能或装备状态。
- 补齐缺失资源前记录可信来源。不得修改 `inputs/official/`；运行资源覆盖必须符合审查、编译、语义校验和目标哈希核对规则。
- 技能或资料生成文件从当前产品源或指定 kRO 源生成，不从历史翻译归档回写，不只手改生成结果。
- 将缺少练级地图、装备获取渠道等内容问题单独登记；影响已承诺职业操作的依赖必须解决，新增大型玩法作为范围决策。

退出条件：目标职业技能资料／资源审计及机制分类代表样本通过，已发现缺陷关闭。按用户要求不逐技能重复实战；记录抽样覆盖范围与独有机制，不能以任意单个技能代替所有类别。

## P5：集成验收与交付

- 按验收计划执行自动化检查及浏览器／游戏实测，记录源码版本、运行资源版本、测试角色条件和结果。
- Client 构建使用 `npm run build -- --all` 或仓库既有等效入口，验证 Gateway 提供新 `dist/Web`，首页仍是启动页。
- 对相关 Server 与 Admin 改动执行适当构建、单元／集成检查；常规职业和现有冒险工具不得回归。
- 构建或部署失败先修复，不用刷新浏览器掩盖旧进程、旧产物或接口版本不一致。
- 若用户要求提交／推送，同步完成各产品仓库 changelog，Client／Server 另按规则更新根仓库集中 changelog；本方案文档不替代这些记录。
- 镜像发布属于后续明确任务，必须按根仓库发布规则完整无缓存构建规定组件的双架构镜像，不能只构建有 Git 改动的组件。

## 执行顺序与风险

建议顺序：P0 → P1 → P2 → P3 → P4 → P5。P0 中与属性和技能有关的发现应尽早反馈设计，避免只开放职业入口后才发现严重能力缺口。

入口与等级改动范围较明确；主要不确定性是技能版本与资源匹配、扩展职业路径、跨职业状态清理。P0 完成后再根据实际缺口估算工作量，不在审计前承诺工期或完整率。

每阶段可以独立验收，但 P1／P2 完成只表示基础入口可用，不表示四转完整支持。验收失败时保留失败场景与状态，不把未测试项改标通过。

## 当前已落地的接口与结算约定

以下约定用于后续实现与回归检查；通过范围仍以进度表的实际证据为准。

- 角色快照增加 `sex`、`jobs` 和 `traits`。`jobs` 由服务端职业数据库按角色性别和规范职业 ID 筛选，每项包含 `id`、`max_base_level`、`max_job_level`、`traits`，排除不可直接选取的形态和婚礼等装扮职业。
- `traits` 包含 `enabled`、`values`、`maximums`、`points`、`budget`；`values` 和 `maximums` 的字段均为 `pow`、`sta`、`wis`、`spl`、`con`、`crt`。
- `character.traits.update` 接收至少一项特性值，服务端合并未修改的当前值后校验单项上限与总预算；成功后剩余点数为预算减去六项合计。`character.traits.reset` 仅重置六项特性与特性点；基础洗点不重置特性。
- 预算按当前服务端等级成长表加转四转奖励点数计算；当前配置在 Base 200 时为 7 点。工具降级时若已有分配超过新预算，则清零六项并返还新预算；仍在预算内则保留分配。退出支持特性的职业时清零特性与特性点。
- `character.progression.update` 先按目标职业校验完整请求，再执行转职和等级变更。高等级角色切回低上限职业必须同时指定合法目标 Base；不隐式降级。降低等级时回收成长点数，未分配点不足以回收时重置基础属性，防止循环升降级复制点数。
- 游戏内采用独立中文导师 `prontera,153,193`。常规路径要求进阶三转、Base 200／Job 70、非宝宝且技能点分配完毕；召唤师路径为 Base 200／Job 60，其余已列扩展前置路径为 Base 200／Job 70。实际分支仍须逐个完成游戏验收。
- 角色数据通过在线角色对象和既有保存机制修改，不以直接写角色数据库替代游戏规则。测试专用角色创建与产品接口行为分别记录。

这些接口由 Server、Admin 和 Client 配套更新；客户端不为旧快照结构保留额外兼容分支。

## 分类抽样记录要求

职业实现状态以[进度表](progress.md)为汇总；测试以机制分类，每个样本记录：

- 源码与资源版本、角色性别、前置职业和初始等级。
- 所属机制类别、选择理由及 NPC 转职、工具切换、成长、特性、AP、保存重登等适用结果。
- 适用装备和形态的检查结果；不适用项说明原因。
- 样本技能与结果、复用同一处理路径的覆盖范围、未覆盖的职业专属差异；未实测项标为“同类抽样覆盖”，不能写成“已逐项实测”。
- 缺陷编号、重现步骤、期望／实际结果、修复位置和复测证据。

生成记录建议放在 `artifacts/fourth-jobs/<批次>/`，资源审计临时产物放在 `work/fourth-jobs/`。目录只有实际执行时才创建，不预造测试报告。

## 测试分层
