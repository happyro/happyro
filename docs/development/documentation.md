# 文档维护

## 单一入口与职责

根仓库 [docs/README.md](../README.md) 是跨仓库导航。产品细节由应用仓库维护，根文档链接其入口；不复制整份 Admin 部署规范或上游框架手册。

| 分类 | 应保存的内容 | 不应保存的内容 |
| --- | --- | --- |
| architecture | 当前数据流、权威边界、设计约束 | 某次构建号和测试通过数 |
| development | 环境准备、命令、测试和协作方式 | 某台主机的密码与临时进程 |
| operations | 服务、配置、备份、发布、排障步骤 | 未验证方案写成已部署事实 |
| localization | 翻译维护源、编码、生效和验证 | 自动推断的译文冒充官方原文 |
| game-data | 各资料来源、输出、消费者 | 重复整篇架构设计 |
| history | 日期明确的缺陷、验收与性能快照 | 新功能长期操作的唯一入口 |

原则：同一规则只有一个主要维护页面，其余用链接。新的说明放入现有分类，只有独立职责确实形成时才新增目录。已无内部引用的转向页可移除；强制规则入口 `operations/docker-release.md` 保持稳定。

## 核对来源

修改命令前阅读真实 Makefile、脚本参数和应用 package.json。查看源码不等于执行通过：将“代码实现”“本机实测”“设计建议”写清楚。样例值不叫运行实际值，历史锁定提交不叫当前产品 HEAD。

代码块默认在根仓库运行；进入产品仓库的命令用 `(cd repos/… && …)` 限定目录，避免下一段误在子目录运行。生成器、重启和发布命令有写入作用，不能混入“只读检查”流程。文档审查不要为了验证文字去启动发布、初始化数据库或修改用户角色。

## 链接与验证

所有新页面从分类 README 可达。移动页面后更新普通 Markdown 链接、代码中的路径和入口说明；历史原始路径应明确标为历史，不伪造其存在性。历史记录保留当时事实，但加醒目的非操作手册说明。

检查清单：

1. 逐项对照相关源码、配置样例和命令参数。
2. 检查本地 Markdown 链接目标与锚点、图片目标、目录索引可达性。
3. 检查涉及的文件路径与 Makefile/npm 子命令存在。
4. 执行 `git diff --check`，核对没有产品代码、密钥或运行数据混入变更。
5. 在审查记录列出未实际运行的构建/发布流程及已知脚本局限，避免“文档通过”被误读为全栈验收。

应用仓库在 `repos/` 下独立检出，本地跨仓库链接需要相应检出才能访问。GitHub 阅读者可从根 README 的远端仓库链接进入。历史证据指向 `work/` 或 `artifacts/` 时仅说明当时位置，不保证任意机器存在。
