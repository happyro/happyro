# 全量 NPC 名称审计与归一化计划

## 目标与范围

统一同一 NPC 在场景名称、对话标题、任务提示、冒险工具、导航和后台目录中的中文称呼，保留不同人物的身份差异与剧情称谓。以下六步是可复用的审计流程，当前一轮已完成约定范围的源码复核与集成验证。过程与验证见[执行记录](execution.md)，历史第二轮问题见[全量校对](proofread.md)，本轮最终范围、验证及保留边界见[全面复核](comprehensive-review.md#本轮最终收口2026-10-24)。

范围固定为当前 Renewal、PACKETVER=20211103 和 kRO 2021-11-05 资源体系。全量盘点同时覆盖服务器内已启用、未启用及条件启用脚本；生产验收优先覆盖实际加载内容。隐藏控制器、传送点、实例复制体和动态改名 NPC 也要登记，但不能为了“中文覆盖率”强行添加可见名称。

## 现有名称链与风险

| 来源 | 审查内容 | 修改原则 |
| --- | --- | --- |
| `repos/happyro-server/npc/` 及运行配置加载链 | 定义名称、duplicate、对话标题、任务文本、动态改名 | 以实际定义及引用关系确定身份，不做全局字符串替换 |
| `repos/happyro-server/src/map/npc.cpp` 与脚本命令实现 | 显示名、内部名称、实例名称和长度限制 | 先确认解析及调用语义，内部标识尽量保持稳定 |
| `repos/happyro-client/src/DB/NpcNameTranslations.zh-CN.json` | 显示翻译、同名异义、残留旧译 | 不用一个全局字符串键合并不同人物 |
| `tools/resources/world/generate-npc-catalog.mjs` | 启用脚本解析、名称转换及目录生成 | 复用现有生成流程；审计清单需补足其未覆盖对象 |
| `configs/npc-navigation-overrides.json` | 导航目标、NPC 身份关联 | 名称变化后检查引用，不手改生成结果补洞 |
| `localization/sources/kro-20211105/` 与 `localization/client/data/` | 任务、导航、地图说明中的 NPC 称谓 | 修改当前源材料，再按现有编译和安装流程验证 |
| 客户端导航目录与 API NPC 目录 | 展示名称及跨端一致性 | 从源生成，检查名称、链接和坐标关联 |

现有目录生成器从 `npc/re/scripts_main.conf`、`conf/script_athena.conf` 追踪加载链，主要收集带地图坐标和外观的定义，并会过滤部分隐藏对象。因此“目录全部审过”不等于“所有 NPC 全部审过”。它还把原始名称纳入目录 ID，改名可能影响导航覆盖项等引用，必须生成旧新 ID 对照并更新实际消费者。

名称中的 `#`、`::` 可能承担隐藏后缀、显示名与内部名称分隔等语义。不能把目录生成器用于展示的截断规则直接用于脚本重写。没有显式独立内部名的定义，显示名修改也可能改变内部查找键；应先查清全部引用，再决定是否使用当前服务端支持的显式内部名形式保持身份。

## 归一化规则

1. 建立经过审核的实体词表，每个人物或角色实体有稳定的审计 ID、标准中文名、源名称、允许称谓、适用地图／剧情及依据。审计 ID 不依赖行号或待修改的显示名称。
2. 相同实体统一译名；不同实体即便英文同名，也不自动合并。职业导师、卡普拉员工等共用职务名可归为同一术语，但仍保留各 NPC 实例身份。
3. 中文采用简体、统一已确定的职业与组织术语，清理无意义空白及混杂标点。专有姓名依据本项目已审校剧情及可核验资源决定，不凭相似拼写猜测。
4. 场景名称与对话标题原则上一致；剧情中合理的简称、身份揭示前的匿名、玩家可自定义名称作为有依据的例外保留。不能把所有 `mes "[……]"` 都当作当前 NPC 自称。
5. 大小写折叠、繁简转换、Unicode 规范化和编辑距离仅用于生成疑似问题，不直接写回名称。格式码、脚本插值和动态参数保留原语义。
6. 不改事件标签、变量、函数、任务 ID、地图 ID、内部控制器名及玩家名称。确需改内部标识时单独列出引用闭包并作为独立变更审核。
7. 中文长度按实际 UTF-8 字节、服务端名称缓冲区与封包限制验证，不仅检查字符数；最终还要验证客户端是否截断或遮挡。

## 实施阶段与交付物

### 1. 冻结基线并建立全量清单

记录七仓库提交哈希、实际配置入口及资源版本。遍历配置 import/npc 链，并额外枚举未加载脚本；追踪自定义配置、运行环境条件、重复定义与移除指令。静态分析应识别注释、字符串与脚本边界，不能只靠正则扫描宣称完成。

为静态定义、duplicate、实例及动态创建／改名调用建立关联；对无法静态求值的表达式登记原因与运行验证场景。结合当前服务端脚本命令实现审查 `getnpcid`、`donpcevent`、`setnpcdisplay`、启停 NPC 和实例名称等引用。无坐标对象、隐藏对象及测试脚本单独分类。

审计与受控修改工具位于 `tools/npc-name-audit/`。无参数只显示符合根仓库规范的帮助。中间清单、差异及截图放在 `work/npc-name-audit/`，不把临时扫描结果放进源目录。

每条清单至少记录：审计 ID、仓库／路径／定位锚点、加载状态、定义类型、地图坐标、原始名称、显示名称、内部名称、对话说话者、任务／导航引用、动态来源、建议标准名、证据、风险、负责人及审核结论。

### 2. 建立术语基准与问题队列

先审校经典初心者和九职业等已有结论，抽取可复用术语；不得把“现有中文”自动认定为正确。输出英文残留、繁简混用、同实体多译、同译不同实体、标题不一致、疑似截断及无来源译名等队列。

先完成一个小批次试点，覆盖普通 NPC、duplicate、动态改名、隐藏对象和任务引用，验证提取器能正确识别身份及引用，再扩大范围。存在争议的实体保留待核验项及原值，不能由各批次自行选译名。

名称归一化规则集中在根仓库 `localization/npc-names/`，由集成人维护；客户端实际名称词表使用唯一 JSON 来源。记录每条规则的适用范围和依据，不建立运行时旧译别名兼容层。

### 3. 分批审计与修改

按“剧情／职业／区域实体关联”划分审计范围，再按文件所有权分配修改范围。同一文件只交给一名修改负责人；跨区域共享脚本、跨任务引用及全局词表统一交集成人处理。每批提供标准名候选、引用清单、补丁及可复现验收场景。

优先级为实际启用且高频的新手／转职／城镇功能，其次副本和活动，再处理未启用脚本。全部都应有审计结论，但未启用内容不能标注为已经完成生产实测。

### 4. 集成与重建

集成人先确认词表及实体映射，再合入相互独立的补丁，更新跨文件引用。源修改结束后统一生成 NPC／导航目录，核对旧新 ID、条目数量、启用状态、坐标和外观；除已批准的变化外不得变化。

使用现有目录工具的 `generate` 与 `check` 子命令；如涉及任务 LUB，使用当前资源回编译流程，完成逐字段语义校验、安装后目标哈希及来源记录。`inputs/official/` 永远保持不变；不恢复旧分片合并回写流程。

客户端需要重建时运行 `npm run build -- --all`，核对 Gateway 正在提供新产物。资源生成和安装期间不得由多个任务写同一目录。

### 5. 验收与交付

- 静态检查：定义和引用可解析，内部名无意外变化／冲突，无新增悬空事件，动态对象有覆盖说明，名称字节长度合法，术语规则及例外无冲突。
- 生成检查：目录可重复生成、相关链接有效，数量和位置变化有解释，源文件与生成物一致。
- 服务端检查：在隔离环境加载实际配置，检查解析、重复名及事件引用错误；验证名称相关分支，不以启动成功代替完整任务测试。
- 游戏检查：桌面和移动端核对场景名称、点击对话、选项、导航和任务提示；覆盖 duplicate、实例、动态改名及剧情称谓。场景默认不常显名称时，通过实际名称请求／显示路径验收，不能据此判定缺名。
- 流程回归：验证商店、仓库、传送、转职及实例关键流程，确认仅改称谓没有破坏交互。任务有共享全局状态时使用隔离环境，避免并发测试互相污染。
- 结果统计：分别报告已加载定义、未加载定义、动态模板、运行实例和文本引用；每类列总数、已审数、已修改数、保留例外及待核验数，禁止混用这些口径计算“完成率”。

只有全量清单都有结论、所有修改通过引用和生成检查、要求的实测已完成，才可宣称相应范围完成；未知动态来源和未验收项必须保留。词表、方案和结论进入版本控制，生成过程及大体积证据留在 work/ 或 artifacts/。

## 并发策略

结论：可以并发，建议“单人定规则与集成，多个审计者分区审查”。不必逐个 NPC 串行处理，也不适合让多个任务同时改全局词表和资源目录。

| 工作 | 是否并发 | 边界 |
| --- | --- | --- |
| 初始全量盘点、身份模型和词表定稿 | 集中执行 | 建立唯一基线与统计口径；扫描计算可并行 |
| 只读名称审计与候选问题整理 | 可并发 | 使用同一基线与词表版本，分区输出，不直接裁决共享术语 |
| 不重叠脚本文件修改 | 可并发 | 独立 worktree／分支或明确文件独占，交付提交和验证记录 |
| 全局翻译表、导航覆盖及共享脚本修改 | 单一写入者 | 各批次提交建议，由集成人消解冲突后写入 |
| 补丁集成、资源生成与安装 | 串行 | 全部依赖已审核词表；禁止多个生成进程覆盖结果 |
| 游戏回归 | 有条件并发 | 独立账号并不足以隔离全局任务状态，必要时独立服务端和数据库 |
| 最终全量一致性检查与发布 | 集中执行 | 针对最终合并后的同一版本，不复用各分支结果冒充最终验收 |

建议试点采用 1 名集成人加 2 名审计者，流程稳定后扩为 1＋3。本轮采用独立文件并发审查与修改，由集成人集中维护共享词表、任务及生成产物。按实体／文件边界分片，而不是机械均分 NPC 数量；共享文件多、动态逻辑密集的批次优先串行。

每个批次应绑定基线哈希、词表版本、独占文件列表、依赖实体和验收记录；上游词表发生变化时，受影响批次重新验证。多人使用同一工作目录时，代码修改必须按文件明确独占，禁止同时写共享文件或操作共享索引；需要独立 Git 操作时使用隔离 worktree。

## 提交与回退

按一个人物群／任务链或一个确定术语形成可独立验证的提交，不按“修改了多少行”切分。服务端、客户端、API 生成目录等在所属仓库提交对应产品日志；客户端和服务端变化同步根仓库集中日志，再同步文档站。提交时按实际改动同步所属仓库记录，不以集中日志替代产品仓库日志。

跨仓库记录一组对应提交及资源哈希，部署时作为同一版本验收。发现引用或流程回归时回退关联源修改及生成资源，不只回退某一张显示表。后续维护保持固定封包与资源边界；本轮实际行为修复及验证边界以全面复核记录为准。
