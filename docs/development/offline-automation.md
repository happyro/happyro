# 服务端自动战斗与离线挂机设计

状态：**设计建议，尚未实现**。2026-10-23 根据当前客户端自动战斗、拾取及地图服会话代码审查整理。本页不是已上线功能说明；实施时更新本文的决策与验收结果，不另外维护相互重复的方案。

## 目标与结论

把自动战斗重构为地图服托管：在线自动战斗与离线挂机使用同一个执行引擎，网页负责设置、启动、停止及状态展示。切换标签页、最小化和关闭浏览器不再承担战斗调度。

“离线”指玩家客户端离线，角色仍是游戏世界中的真实角色。其他玩家能看到它，角色正常受到攻击、消耗 SP／弹药／材料，获得经验与掉落，也可能死亡。离线不等于免伤、收益模拟，也不保证服务器停机期间继续运行。

普通手动操作继续保留；自动战斗最终只保留一套服务端实现，不长期维护客户端和服务端两套策略，不引入旧设置格式兼容或历史数据迁移。

| 方案 | 适用性 | 决策 |

| 为每个角色运行无头浏览器 | 需维护浏览器进程、登录凭据与网络会话 | 不作为正式生产方案；无头浏览器继续用于测试 |
| 地图服托管真实角色 | 使用既有战斗、寻路、掉落和地图生命周期 | 推荐 |
| 按离线时长计算奖励 | 不执行实际战斗与拾取 | 属于另一个离线收益产品，不混入本功能 |

## 推荐架构

### 客户端与控制接口

客户端保留怪物筛选、技能列表、搜索／活动范围、拾取过滤、瞬移条件等设置界面。设置由服务端校验并返回实际生效值；界面不根据本地按钮状态宣称服务器已开始挂机。

控制接口提供配置、启动、停止、查询及接管。请求校验身份、角色归属、当前控制状态和权限；使用幂等请求标识及状态代次，防止重试或旧页面重复启动。API 可承担认证、命令记录与查询，但实际在线角色状态只能由地图服主线程修改，不通过 SQL 绕过游戏服规则。

### 地图服执行引擎

地图服维护一个自动行动状态机，协调寻找目标、追击、攻击／施法、拾取、等待与受限瞬移。目标失效后重新选择，寻路失败短期避让；不在每个调度周期重新开始已有攻击或寻路。

抽取公共角色行动入口，让手动操作与挂机经过相同业务校验，再进入既有移动、普通攻击、技能使用和拾取函数。不能仅调用 `unit_attack`、`unit_skilluse_id`、`unit_skilluse_pos` 或 `pc_takeitem` 就假定覆盖了原封包入口的全部校验。

必须保持攻速、冷却、施法时间、射程、障碍、SP、弹药、材料、负重、物品归属、状态限制及地图规则。经验与掉落来自原有真实战斗链路，不另写一套挂机伤害或奖励计算。

### 控制权与会话生命周期

建议显式状态为：手动操作、在线自动战斗、离线挂机、接管中、已停止。角色任何时刻只有一个控制者；会话状态变更与自动行动取消在地图服主线程串行完成。

进入离线挂机必须得到服务端成功回执。随后关闭网页只解除网络连接，保留真实角色及挂机控制器。不能依赖网页 unload 回调作为启动或停止的唯一保证，也不能把普通掉线一律解释成无限期挂机授权。

重新登录时先验证账号所有权、冻结自动行动并处理会话交接，再把玩家连接交给原角色。不能生成第二个角色实例，不能让旧页面继续发送行动。需要明确处理重复登录、多标签页、切换账号、角色选择和角色删除限制。

离线摆摊标记保持自身语义，不继承其免伤、怪物忽略或专属登出逻辑。后台应区分“在线操作”“在线自动战斗”“离线挂机”，避免把挂机角色误计为已退出世界。

## 建议默认行为

以下为方案默认值，尚未成为产品配置。

| 事件 | 行为 |
| --- | --- |
| 在线自动战斗，切后台或最小化 | 服务端继续执行，不依赖页面可见性 |
| 主动选择离线挂机 | 服务端确认接管后可关闭网页 |
| 未开启离线挂机便断线 | 不转为无限期离线挂机，按明确的断线停止策略处理 |
| 重新登录同一角色 | 暂停挂机，进入原角色，玩家决定是否继续 |
| 手动移动、攻击、技能、交易或 NPC 操作 | 先按统一规则暂停／停止自动行动，再执行手动操作，禁止双控制器竞争 |
| 死亡、背包满、负重超限或持续无法执行 | 停止并记录原因；首版不自动复活／回城出售 |
| 地图服重启或崩溃 | 保留配置和可恢复状态，默认不自动重启战斗，不补算停机收益 |
| 角色权限被撤销、封禁或达到挂机期限 | 服务端停止并保存角色，客户端无需在线 |

断线宽限、最大时长、单账号并发额度和负载上限须在实现前确定；本文不虚构已经存在的环境变量或额度。建议首版每账号只允许一个挂机角色，并采用可明确解释的有限时长。

## 持久化与收益

保存当前挂机配置、运行状态、状态代次、开始／结束时间及停止原因。当前目标、路径、正在执行的动作属于临时状态，重启后不重放。各服务重连必须核对控制归属，避免多个地图服同时认为自己拥有角色。

背包、金币、经验继续使用角色保存机制。挂机汇总记录实际已发生的结果，重新登录不再补发一次奖励。崩溃时以实际持久化的角色状态为准；不能宣称统计记录等价于严格不丢失的奖励账本。

停止、保存和断开会话的执行顺序须明确，处理保存失败与未知结果，不盲目重试有副作用的动作。实现需要的新持久化结构属于当前功能，不增加历史数据兼容分支。

## 地图切换与资源恢复

离线角色没有客户端，不能等待 `LoadEndAck` 或地图渲染完成才能继续活动。需要明确分离“服务端实体转移完成”和“在线客户端场景加载确认”。离线传送由地图服完成角色放置及正常地图规则处理；玩家接管时重新走在线地图加载协议。

接管遇到缺图仍使用[地图加载失败恢复](map-load-recovery/README.md)：返回成功位置或普隆德拉。此时暂停挂机，不能让恢复过程与自动瞬移相互竞争。不得伪造客户端加载确认来绕开当前保护。

首版限制在明确允许的普通野外地图；不开放副本、PvP、攻城及需要 NPC 对话的任务。跨地图服转移、实例销毁、组队与掉落归属都必须单独审查；未覆盖的路径应明确拒绝，不默默按普通地图执行。

## 调度与性能

使用地图现有空间索引查询附近实体，避免每个角色反复扫描整张地图。保留当前有效目标，对搜索和寻路做分散调度、预算限制及短期失败避让。无目标时降低扫描频率，不忙循环。

决策频率不等于攻速：调度器选择动作，既有攻击／技能计时器控制动作何时执行。角色状态及战斗结算仍在地图服主线程；不能以多线程直接修改角色、怪物或背包。

压测至少观察地图服延迟、目标搜索及寻路耗时、定时器积压、存档延迟、内存、断线接管耗时，并覆盖高密度共享地图。承载上限依据压测设置，不能按开发机性能预先承诺人数。

## 实施阶段与验收门槛

### 第一阶段：服务端在线自动战斗

保留现有 UI，迁移找怪、攻击／技能、拾取和瞬移决策，抽取公共行动校验。以现有行为用例验证规则，再增加真实战斗测试。完成后停止运行旧客户端自动战斗策略，不长期保留双实现或旧参数别名。

验收：前台、后台、最小化行为一致；手动操作能正确接管；攻击／技能成本和冷却不被绕过；目标消失、路径受阻、物品归属、满包与地图限制均有明确结果。

### 第二阶段：离线托管与接管

实现脱离 socket 的挂机会话、持久化、明确停止原因及原角色重连接管。

验收：关闭浏览器后真实击杀和拾取继续；重连是同一角色且不双重执行；覆盖多标签页、重复请求、意外断线、死亡、封禁、保存失败、服务重启及离线传送。登录缺图能恢复，恢复时不会继续自动移动。

### 第三阶段：运维与容量

增加后台状态、停止操作、挂机汇总、期限／容量限制和压力测试。后台操作遵循现有权限与审计机制，不提供任意玩家绕过地图服规则的 SQL 修改。

验收：高并发仍保持正常地图响应；停止和接管延迟可测；汇总不重复发奖；所有异常停止可追溯。将实测能力写入上线说明，再决定是否扩展到特殊地图和更多技能类型。

## 实施前需要确定的产品规则

- 首批允许的地图与技能类型；特殊技能、召唤物、队伍辅助是否纳入。
- 离线挂机最大时长、每账号角色数、断线宽限和服务端容量。
- SP／弹药耗尽时停机还是等待；是否允许补给及具体消耗规则。
- PK、死亡、组队和掉落分配的规则，以及管理员停止后的玩家提示。

本设计不自动开启上述扩展。推荐先完成服务端在线自动战斗，再开放离线托管，最终保持同一套游戏规则和执行引擎。
