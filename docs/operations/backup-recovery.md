# 备份、恢复与回滚

Git 和镜像不包含玩家存档。`work/` 既有可重建产物，也有数据库、密钥和运行状态，禁止整体当作缓存删除。

## 先确定备份目标

| 数据 | 本机常见位置 | 处理 |
| --- | --- | --- |
| 游戏与后台数据库 | `happyro-mariadb` 的 `/var/lib/mysql` 挂载 | 一致性数据库备份，包含 happyro、happyro_log、happyro_admin |
| 完整 Docker 游戏栈数据库 | `happyro-database` 的 `/var/lib/mysql` 挂载 | 与本机开发库分别识别，不混用目录 |
| 运行配置和凭据 | `work/runtime/mariadb-10.11/`、Gateway `.env`、Admin `.env`、systemd 单元 | 受限权限备份，不提交、不打印秘密 |
| 已审查运行资源 | `inputs/runtime/kro-20211105/` | 保留部署文件及源/目标哈希，官方只读源另行保管 |
| 构建与代码 | 各仓库提交、PWA manifest、镜像 digest | 记录可复现版本，不能代替数据库 |

确认实际挂载（只读）：

```bash
docker inspect happyro-mariadb --format '{{json .Mounts}}'
systemctl show happyro-map happyro-gateway -p FragmentPath -p ExecStart
```

未部署的容器不存在是正常情况，不能因此新建空库“修复”。根仓库目前没有自动备份、恢复命令，也没有定期备份保证。

## 一致性备份流程

1. 确认维护窗口，记录所有仓库提交、数据库版本和挂载位置。
2. 停止游戏写入与 Admin 写操作；按现有单元类型停止 map / char / login / web，等待角色保存完成。
3. 使用有相应权限的数据库账号执行 `mariadb-dump`，包含游戏、日志与后台库及触发器、存储过程、事件。凭据通过受限配置文件或环境传递，不放进命令行或文档。混合 MyISAM/InnoDB 时，不能仅用 `--single-transaction` 声称全部表一致；停写并使用适合表引擎的锁定方案。
4. 或在全部写入服务停下后停止数据库，备份明确验证的数据库卷和配置；不要直接复制运行中的数据库目录当作可恢复备份。
5. 将备份放到独立存储，记录 SHA-256、时间、大小和恢复所需配置。先校验备份有效，再恢复服务。

## 恢复演练

在隔离的数据库实例和新数据目录恢复，使用不同端口与隔离的游戏配置，不能让测试 map-server 接入正式角色服。核对表引擎、schema、账号/角色、背包、邮件、日志与 Admin 登录。完成实际恢复演练后才将备份标记为可恢复。

正式恢复前保存事故现场，确认目标实例与备份时间；恢复会替换此时间点之后的数据，必须明确其影响。重新初始化数据库不是恢复。

## 应用回滚

静态 PWA、Gateway 和 Server 可以切回已验证提交/镜像并重建或部署，但仍需考虑数据库迁移兼容性。回滚前核对 schema；不可逆迁移需要备份恢复或向前修复，不能只回退二进制。

客户端入口必须是完整 `--all` 启动页，更新后执行构建哈希验证并在浏览器确认。Docker 发布与回滚使用统一版本和明确 digest，不以 `latest` 作为历史版本证据，规则见[镜像发布](docker-release.md)。
