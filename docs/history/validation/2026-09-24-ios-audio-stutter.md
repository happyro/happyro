# iOS 攻击音效卡顿调查（2026-09-24）

状态：已实现全局 Web Audio 短音效播放与相关清理／动画修复，并部署本机。2026-09-25 已通过 iPhone Chrome 实机验收，用户确认“已经流畅，音效正常”；本机 Chrome 与 WebKit 自动化音频验证通过。修复后的 iPad、iPhone Safari 尚未单独进行实机复测。

本文保留修复前实机证据，并记录修复实现和验证边界。后续采集操作见[移动端性能日志回传](../../development/mobile-diagnostics.md)。

## 现象与影响范围

- 用户反馈 iPhone、iPad 的 Safari 和 Chrome 在攻击时均有明显卡顿，表现为整个画面停顿；桌面端没有同样的明显问题。
- 本次收到的实机日志来自 iPhone Chrome 和 iPhone Safari。iPad 的现象来自用户反馈，尚未单独采样验证。
- 关闭游戏内“音效”后，用户确认卡顿明显改善。用户需要保留战斗音效，关闭音效仅作为排查对照和临时缓解方法。

## 测量含义

- `audio.play.cached` / `audio.play.new`：围绕 `sound.play()` 调用前后测量的耗时。242ms 发生在调用返回之前，缓存命中也会触发。该值是经过时间，可能包含系统调度等待，不等于纯 CPU 指令执行时间。
- `audio.play.ready`：从调用开始到播放 Promise 完成的等待时间，不能当作主线程阻塞时长。
- `perf.summary.cpuMs`：游戏渲染回调开始到结束的经过时间；`intervalMs` 是实际游戏渲染帧的间隔。60 帧目标下每帧预算约 16.7ms，长时间未返回的音效调用足以拖延下一帧。
- `damage.texture`：伤害数字 Canvas 处理和 WebGL 上传调用的耗时，不是 GPU 执行时间。
- 详细慢调用和长帧事件有数量上限；统计长帧次数应使用 `perf.summary.intervalMs.over50`，不能只数 `perf.frame-gap` 行数。

诊断实现见 [CombatDiagnostics.js](../../../repos/happyro-client/src/Core/CombatDiagnostics.js)。

## 代码中的问题路径

当时的 [SoundManager.js](../../../repos/happyro-client/src/Audio/SoundManager.js) 使用 HTML `<audio>` 播放 WAV 短音效：缺少可复用播放器时创建新元素，播放结束后重置播放位置并放入缓存，下次命中缓存继续调用 `.play()`。

已确认的两个问题点：

1. 复用播放器没有消除慢调用。日志中的最高 242ms 来自 `audio.play.cached`，因此仅增加文件预加载或播放器缓存不足以解决已观察到的停顿。
2. 100ms 同音效间隔和实例数量限制仅在新建播放器的加载回调中检查；缓存命中分支直接播放，绕过这些限制。这是可能放大密集战斗负载的代码因素，尚未单独测量其影响。

[EntitySound.js](../../../repos/happyro-client/src/Renderer/Entity/EntitySound.js) 根据实体动画触发音效，[Damage.js](../../../repos/happyro-client/src/Renderer/Effects/Damage.js) 也使用音效管理器。音频调用卡住时，影响会表现为整帧停顿，而不只是声音延迟。

## 为什么桌面端表现不同

相同的 JavaScript 媒体接口会进入不同平台的浏览器和系统音频实现，调用成本可能明显不同。Chrome 官方说明其 iOS 版本使用 WebKit，与其他平台的 Chrome 架构有差异；换用 iOS Chrome 不等于切换到桌面 Chrome 的媒体实现。

目前日志确认了 iOS 上 `.play()` 返回前的显著延迟，但尚未取得浏览器原生调用栈。具体慢在媒体进程通信、音频会话激活还是系统调度，仍是待验证项；不能笼统归因于“手机性能差”，也不能将某个 WebKit 已知问题直接认定为本次根因。桌面浏览器的触控模拟仅验证采集链路，不替代真实 iOS 性能验收。

## 修复实现：全局使用 Web Audio 播放短音效

移动端和桌面端统一使用 [BufferSoundPlayer.js](../../../repos/happyro-client/src/Audio/BufferSoundPlayer.js)，[SoundManager.js](../../../repos/happyro-client/src/Audio/SoundManager.js) 保留游戏调用入口。背景音乐仍由独立 BGM 模块管理。

- 音效资源异步加载并解码为 `AudioBuffer`，相同文件合并加载和解码；角色 ACT 音效表及武器音效提前准备。攻击触发只创建音源和增益节点、关联已有缓冲区并调用 `start()`，不再使用 HTML 音频元素播放这些短音效。
- 一个长期存在的 `AudioContext` 在用户操作时激活。切后台、中断、切图或停止指定音效时停止对应播放并清除待播请求；恢复后播放新事件，不补播过期攻击音效。未准备好的音效仅保留最近一次触发，准备耗时超过 250ms 时放弃该次播放，但保留缓冲区供下次使用。
- 缓存最多 32MiB 解码样本／128 项，最多同时准备 4 个资源，按最近使用情况回收未播放的缓存；最多 32 个播放节点、同一文件最多 8 个重叠实例，同类重复触发间隔为 30ms。玩家自身位置的音效在拥挤时优先替换其他实体音效；70ms 攻击间隔可正常连续触发。
- 总音量与距离衰减分别控制，避免调整音量时重复相乘；关闭音效不会把保存音量改成零。修正武器音效赋值对象，以及隐匿音效的位置参数传递。
- 内存清理改为每渲染帧最多检查 5 个缓存条目，并在 2ms 预算用尽时让出；单项释放本身仍可能超过预算。删除前重新检查最近使用时间，清理不再依赖 `requestIdleCallback`，资源释放异常也不会留下永久忙碌状态。
- 修正身体动作在本帧中途切换后，其他部件使用旧渲染时间计算出负动画帧索引的路径。测试复现了这个边界；它与此前缺少完整消息的那条实机异常是否为同一次原因，仍无法追溯确认。
- 移除默认逐包收发控制台输出，保留显式封包转储功能，减少诊断采样对战斗的干扰；错误记录同时保存名称、消息和堆栈。

## 下一轮优化方向（已记录，暂不实施）

2026-09-25 用户要求先记录方向并提交当前修复，暂不继续优化。本节仅记录后续排查计划，不代表已经新增采样或确认新的性能根因。

### 剩余长帧的证据

沿用上述会话和 `elapsedMs=52904` 统计边界：35.064 秒内的 2,001 个帧间隔中，有 6 次达到 57–68ms，渲染循环的同步经过时间最高 59ms。6 条详细长帧记录均邻近玩家自身的 `kind=10` 暴击事件，攻击动作时长字段 `attackMs=70`：

| 长帧记录 elapsedMs | 帧间隔 | 距最近一次暴击事件 |
| --- | --- | --- |
| 26366 | 57ms | 67ms |
| 28127 | 68ms | 75ms |
| 29325 | 65ms | 71ms |
| 31186 | 58ms | 67ms |
| 31856 | 61ms | 70ms |
| 32911 | 66ms | 72ms |

这里的 57–68ms 是实际游戏帧间隔，不是攻击动作时长。暴击与长帧的时间关联值得追踪，但不能证明是暴击特效导致，也不能把 5 秒汇总窗口的渲染最大值直接对应到某一条长帧。同一组窗口中，`audio.start` 最高 1ms、`damage.texture` 最高 1ms、`mobile.hud` 最高 2ms，尚未显示这些已计时部分存在明显同步慢调用；纹理上传调用的经过时间也不能代表完整 GPU 绘制耗时。

### 排查优先级

1. **拆分战斗渲染耗时。** 对帧内事件执行、实体动作／动画更新、命中与暴击特效、伤害显示的完整渲染过程分别计时，关联同一帧及攻击事件。优先观察当前未被 `damage.texture` 覆盖的阶段，区分首次出现与重复攻击。
2. **检查精灵和特效纹理处理。** 记录资源解析、纹理创建／上传／释放的同步耗时和触发数量，确认是否在命中时反复准备相同资源。只有证据指向这里时，再决定是否调整预加载、缓存或对象复用。
3. **检查清理尖峰。** 记录缓存扫描、单项资源释放的耗时、条目数量及发生帧。现有每帧 5 项／2ms 限制不能保证单次释放不超时，收集键列表也需要单独观察；尚无证据证明本次 6 个长帧来自清理。
4. **补足帧外原因与测量开销。** 若上述同步计时不能解释停顿，再结合浏览器性能录制检查垃圾回收、页面布局、GPU／合成与调度等待，同时对照调试采样和上传本身的开销；不根据帧间隔单独认定具体原因。

### 复测与验收

- 固定同一设备、浏览器、地图、画质和方向，保持音效开启，分别采样普通攻击、暴击、高攻速与多怪场景；同时覆盖首次触发及资源已准备好的重复触发。
- 分段计时只在调试模式启用，限制详细日志数量，沿用每窗口汇总及自动回传；不恢复默认逐包日志，避免诊断本身增加明显负担。
- 对比相同长度窗口中的帧间隔 P95／P99、达到或超过 50ms 的次数、最慢渲染阶段及其与攻击的关系；分位数不能直接跨窗口平均。优化应有可重复证据，并保留音效、动作和命中显示的正确时序。
- 找到热点后再实施对应优化，并回归桌面端及移动端。iPad、iPhone Safari、锁屏恢复与较长时间战斗仍需补充独立实机覆盖。

## 扩大覆盖范围时的回归要求

- 在同一台手机、同一浏览器、同一地图与战斗场景下，固定画质和方向，执行音效开启、关闭、再开启的对照；分别覆盖 iPhone / iPad、Safari / Chrome。
- 保持音效开启，验证普通攻击、高攻速连击、技能和多怪战斗，观察声音与动作同步，以及关键音效是否丢失。
- 对比帧间隔 P95/P99、最大值、达到或超过 50ms 的次数，以及音效启动耗时；目标是接近关闭音效时的画面流畅度，消除攻击反复触发的百毫秒级停顿。
- 单独验证首次播放与缓存命中、音量调整、切图、重登、锁屏和切后台恢复；同时检查长时间战斗的内存增长和背景音乐共存。
- 本次已完成桌面端音效回归和 iPhone Chrome 实机验收；新增 iPad、Safari 或锁屏恢复等实机样本时，补充设备与浏览器信息及采样证据。
