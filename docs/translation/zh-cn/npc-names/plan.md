# NPC 名称翻译计划

## 目标

统一 HappyRO 常用城镇中玩家可见 NPC 的中文名称，建立可复用的名称术语表，并保证悬停名称、名称牌、对话标题和导航文本使用一致译名。

## 实施阶段

### 第一阶段 A：核心六城名称种子

先登记六城常用、公共和剧情入口 NPC，为后续逐城全量覆盖建立术语基础：

- `prontera`：普隆德拉
- `geffen`：吉芬
- `morocc`：梦罗克
- `payon`：斐扬
- `alberta`：艾尔贝塔
- `izlude`：依斯鲁得

这一阶段只代表“部分覆盖”，不能标记为整张地图已实现。

### 第一阶段 B：核心六城逐城全量覆盖

每次只处理一个城镇，明确主地图及关联室内地图，生成服务端活动 NPC 的完整英文基础名称清单，然后补齐客户端映射并完成实机验收。

普隆德拉是第一个按此标准完成的城镇。吉芬、梦罗克、斐扬、艾尔贝塔和依斯鲁得仍需分别执行同样流程。

### 第二阶段：其他主要城市

扩展到 `aldebaran`、`yuno`、`comodo`、`rachel`、`veins`、`einbroch`、`lighthalzen`、`hugel` 等主要城市。每座城市独立定义范围和验收，不再用合并估算数直接标记完成。

### 第三阶段：其他常用城镇

扩展到 `amatsu`、`louyang`、`gonryun`、`umbala`、`brasilis`、`dewata`、`malaya`、`moc_para01` 等地图。

## 翻译规则

1. 只翻译玩家可见名称，不修改脚本函数名、标签、资源名、地图键和内部标识。
2. `NPC名称#internal_id` 只翻译 `#` 前的显示名称；`#...` 和 `::...` 必须保持不变。
3. 客户端名称表负责实体悬停名称和名称牌；服务端 `mes "[名称]"` 负责对话标题。两条来源都必须使用同一译名。
4. 不为解决客户端悬停英文而批量改写服务端 NPC 定义名，避免破坏 `duplicate()`、`enable/disable` 和事件引用。
5. 同一个英文名称优先使用统一译名；有官方或项目术语时以 `terms-names.csv` 为准。
6. 英文名称超过 23 个字符时，必须验证 24 字节名称封包截断后的别名仍能命中译文。
7. 重复 NPC 按英文基础名称去重，但覆盖检查必须包含目标范围内的每个活动实例。

## 单城完成条件

只有同时满足以下条件，进度才能标记为“全地图已实现”：

1. 批次文档列出主地图、关联室内地图和明确排除项。
2. 从服务端当前活动脚本生成全量 NPC 名称清单，并完成人工可见性分类。
3. 所有英文基础名称均能命中客户端中文名称表，自动检查缺失数为 0。
4. 所有超长英文名称均通过 23 字符截断映射检查，且不存在译名冲突。
5. 客户端构建和名称表测试通过；如修改服务端脚本，服务端构建也必须通过。
6. 在主地图和各类关联室内地图抽查悬停名称、名称牌、首次对话及多页对话标题。
7. NPC 对话、商店、传送、任务和导航功能未因名称处理失效。

只通过服务端构建、只登记术语表或只抽查少量常用 NPC，均只能标记为“部分覆盖”或“待实机验收”。
